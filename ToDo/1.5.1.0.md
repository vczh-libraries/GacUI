## Support `<Raw/>` element on all platforms

- In remote protodol, a `Raw` element is used to sync text data to the renderer.
  - Currently raw element in XML will map to `GuiDirect2DElement` and `GuiGDIElement` dynamically, keep this.
    - `GuiRemoteRendererSingle` will have to use the same way to create a raw element, so that the actual implementation decision could be kept inside any native platform, `GuiRemoteRendererSingle` doesn't need to know the details.
  - Make a raw element base class `GuiRawElement`:
    - Add a `WString Data` property.
    - Add a `WString Id` property.
    - No `DataChanged` or `IdChanged` is needed.
    - Changing `Data` will trigger repaint, changing `Id` will not.
  - Current `GuiDirect2DElement` and `GuiGDIElement` should inherit from this `GuiRawElement`.
  - `GuiRemoteRendererSingle` should expose a collection by `const List<Ptr<GuiRawElement>>& GetRawElements() const`, with `RawElement(Installed|Uninstalled|Changed)` events for accessing all raw elements. When `Installed` raises, the `Ptr<GuiRawElement>` field in the event args should already appear in `GetRawElements`. When `Uninstalled` raises, that field should still in `GetRawElements` and it will be removed from the list after all `Uninstalled` handlers are executed.
    - Both `Id` or `Data` changing raise `RawElementChanged`, just like how changing other elements is working, but the event does not need to point out which property is changed.
    - Events are generated from the remote renderer, no protocol messages for them.
      - Remote protocol should add messsages for raw elements just like other elements.
    - `GuiRemoteRendererSingle` will have events for `RawElement(Installed|Uninstalled|Changed)`.
  - TUI will not support raw element. No raw element renderer should be added, using raw element with TUI is expected to crash because of this.
  - In the remote probocol based unit test, add one test case to like, press a button and change `Id`, press another button and change `Data`.
    - In the native unit test snapshot viewer, a raw element should be implemented by an label without linewrap and with ellipse, so that we can actually see `Id: Data` in the viewer.
- On `FullControlText` draw a clock, copy from `GacUI_Windows/Direct2DClock` tutorial, but it is driven by the text data.
  - A timer will update the data to store time for every second, and because changing data triggers repaint, so the repaint event should just draw a clock according to the data, and the clock automatically looks live.
  - Drawing can only be done with C++, so some manual code is needed, accessing native rendering devices with XML is impossible.
  - We need to handle Direct2D and GDI, it is easy to use `dynamic_cast` on the `GuiRawElement` and use api directly.
  - A function should be exposed from `Test/GacUISrc/Generated_FullControlTest/FullControlTestRawElement.(h|cpp)`, calling it will attach to the raw element, inside it all handlers will be attached according to the type of the actual implementation, you are going to implement Direct2D and GDI at the same time, no platform guard is needed you can assume this file is windows only.
  - NO NEED to update `DebugRemoteProtocolSop.md`, this page will not be included, it is for human verification.
- Work on `GacJS` to support it.
- Verify on native renderer
  - Direct2D
  - GDI
  - Wayland (`GuiWaylandElement`), `FullControlTestRawElement.cpp` from `GacUI` will not be copied by `syncProj.sh`, its own version will be created and maintained in `wGac` repo.
  - Cocoa (`GuiCocoaElement`), `FullControlTestRawElement.cpp` from `GacUI` will not be copied by `syncProj.sh`, its own version will be created and maintained in `iGac` repo.

### Step 1

There is a known issue when handling mouse events on a composition, the handler deletes the composition, and GacUI will crash. This is expected, and point events will be handled just like how mouse events are handled, it will have the same issue, and this is also expected. When implementing point events, you are going to figure out if any code for mouse events could be reused for propogating and capturing. GacUI will offer a pair of new capture/release functions for point events, they work like how captures are done to mouse events.

- Use point as the term as we dont use legacy touch on both Windows and browser.
- Add all point events to `INativeWindowListener` with Windows implementation.
  - gesture will not be included in this version.
- A point sequence begin and point sequence end event before and after a series of point events, when an event share at least one finger with the next event.
  - Point sequence begin starts with the first finger, it will be used to query id that position supporrs touching, responsing "No" will stop reporting all following events.
  - A sequence has an unique id per native window.
  - Not supported sequence begin also denies gesture.
- Maps events to `GuiGraphicsComposition`'s event receiver:
  - The first point locks the composition receiving point events for the complete sequence.
  - It also handles the point sequence begin event, and the event handler needs to declare if it accepts point events. Such information will be reported back to `INativeWindowListener`, with the same behavior, which is when the composition does not accept point events, all subsequence events will not raise.
- `FullControlTest` has a dedicated page to demo with single point to drag, with two finger to move, rotate and zoom.

  - Raw element will be used here, and it only works on Direct2D renderer. Logics need to be done in C++ code.
