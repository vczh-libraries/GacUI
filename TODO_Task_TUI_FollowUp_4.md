## TuiControllerBase renderer clipping

- Currently the TUI render target supports clipper.
- Clipping must be implemented in VlppOS's TUI instead of in render target.
  - In this way we could keep DRY.
  - A clipper will be passed to any drawing functions. It could be a TuiClipper struct with x1,y1,x2,y2 in `vint`.
    - In drawing functions, we can first create a clipper equals to the buffer range, and see if null pointer comes in, if not do intersection.
    - In drawing functions such "normalized" clipper will be first calculated and then draw.
  - Render target could just simply calling them in this way.

### DETAILS

- The existing raster clipping belongs to `TuiGraphicsRenderTarget` in `Source/PlatformProviders/TUI/TuiGraphics.cpp`. Keep the render target's composition clip stack (`PushClipper`, `PopClipper`, and effective-clip queries); move the drawing primitives' clipping into VlppOS. The stack still defines the clip passed to each drawing call.
- Add `vl::console::TuiClipper` alongside the TUI drawing types in `../VlppOS/Source/TUI/TUI.h`, with `vint` coordinates and half-open bounds `[x1, x2) x [y1, y2)`. Append an optional `const TuiClipper*` parameter, defaulting to `nullptr`, to both the active-buffer and explicit-buffer overloads of every drawing operation: `TUI::PrintChar`, `TUI::Clear`, `TUI::DrawLineV`, `TUI::DrawLineH`, and `TUI::DrawRect`. Rounded corners remain an option on `TUI::DrawRect`.
- Normalize the clip against the current buffer dimensions inside VlppOS. Null means the whole buffer; empty, inverted, or disjoint intersections paint nothing. Preserve existing argument validation even when nothing is visible. Existing inclusive drawing endpoints remain unchanged; GacUI converts its exclusive rectangle edges once when forming those endpoints.
- Clip the original geometry, rather than replacing its endpoints with the clip bounds. In particular, a clip inside a rectangle must not create new edges or corners. Preserve line merging, rounded-corner rules, one-cell-wide/high borders, and the existing GacUI 1-by-1 border no-op.
- Preserve width-two cell invariants. A new wide glyph requires both cells inside the normalized clip before any mutation. Overwriting an existing lead or continuation cell may clear its partner immediately outside the clip, as required by the existing wide-cell repair contract; this is the only permitted repair spill outside the clip. Keep the partner's background and leave unrelated cells untouched.
- VlppOS TUI colors do not contain GacUI alpha. Retain GacUI's destination-dependent RGB blending, transparent no-ops, text styles/backgrounds, and caret behavior. Any destination reads in the render target must still be in bounds before calling the clipped primitive. Reacquire the buffer and dimensions for each operation, including after nested resize callbacks. Do not introduce GacUI types into VlppOS.
- Replace the full-buffer scratch copy used for opaque borders with direct clipped VlppOS drawing. Keep any alpha-specific work proportional to affected cells; do not retain a second implementation of geometry clipping in GacUI.
- Make upstream changes in the sibling VlppOS source repository, follow its guidance, and regenerate its release and GacUI imports through the supported dependency workflow. GacUI compiles `Import/VlppOS.*`; editing only the sibling source does not update its dependency. Do not hand-edit generated release/import files. Update the owning TUI API/KB documentation when implementing the new contract.

## TUI Color Theme

- Add multiple predefined color options, allow changing them on the fly in `TuiControlTest`.
  - This is done by asking every window to recreate control templates recursively.
- General implementation:
  - Currently we have a `CreateDefaultColorPackage` for sky blue. We need to create:
    - `CreatePinkColorPackage`
    - `CreateOrangeColorPackage`
    - `CreateGrassPackage`
    - `CreateEmeraldPackage`
    - `CreateSkyblueColorPackage`
    - `CreatePurplePackage`
  - All these colors will not be pure and extreme colors, you need to pick a good one, you may want to get the idea from the internet.
  - And you will find them sharing a lot of code, so a internal function `CreateColorPackageInternal` could be created and every function just calls it.
  - `CreateDefaultColorPackage` will then call `CreateSkyblueColorPackage` internally.
  - Now we need a function to recreate control themes. Calling `SetColorPackage` won't update any existing color, the easiest way is to recreate all control themes.
    - `GuiApplication::RefreshThemes` function will be added for this, in this way it find all living `GuiWindow` instances and call its `RefreshThemes` function.
    - `GuiControl::RefreshThemes` will recreate theme inside recursively to all sub controls. A menu button doesn't need to care about its dropdown as it will be taken care of by `GuiApplication::RefreshThemes`, and a dropdown is not technically a child control of menu button anyway. So the implementation should be straight forward.
    - `GuiControl::RefreshThemes` should only work when its `ControlTemplate` is not assigned, as this property is designed to override the theme. Ideally it should just call `RebuildControlTemplate` for itself and recursively call other `RefreshThemes`.
- Verification
  - In `TuiControlTest`'s `Window Manager` page, split the page in half horizontally and in the right side we could put a group box with radio buttons listed in a vertical stack, set to `SkyBlue (default)`. When any button is clicked, it calls `SetColorPackage` and `GetApplication()->RefreshThemes` in `InvokeInMainThread`.
